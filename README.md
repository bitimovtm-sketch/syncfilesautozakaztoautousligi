# Bitrix24 Deal Files Sync (OAuth edition)

Передаёт файлы из 5 полей сделки с портала 1 (`autozakaz.bitrix24.ru`) на портал 2 (`autouslugi25.bitrix24.ru`). Поиск сделки на портале 2 — по полю «Номер кузова».

## Почему OAuth, а не вебхук на портале 1

Поля типа «Файл» в CRM скачиваются ТОЛЬКО методом `crm.controller.item.getFile`, который не работает через входящие вебхуки (возвращает 401/404, проверено). `disk.file.get` эти файлы тоже не видит (ERROR_NOT_FOUND — это другая система хранения). Единственный рабочий путь — OAuth-токен локального приложения.

Портал 2 остаётся на входящем вебхуке: запись файлов через `crm.item.update` работает без OAuth.

## Настройка: локальное приложение на портале 1

1. На портале 1: **Разработчикам → Интеграции → Создать → Локальное приложение** (вкладка «Другое» → «Локальное приложение»).
2. Тип: **серверное** приложение.
3. **Путь вашего обработчика**: `https://<ваш-домен>.up.railway.app/install`
4. **Путь для первоначальной установки**: тот же `https://<ваш-домен>.up.railway.app/install`
5. Права (scope): `crm`
6. Сохранить → скопировать **client_id** (вида `local.xxxx.yyyy`) и **client_secret**.

## Переменные Railway

| Переменная | Значение |
|---|---|
| `P1_DOMAIN` | `autozakaz.bitrix24.ru` |
| `P1_CLIENT_ID` | client_id локального приложения |
| `P1_CLIENT_SECRET` | client_secret локального приложения |
| `P1_REFRESH_TOKEN` | сначала пусто; заполняется после установки (см. ниже) |
| `PORTAL_2_WEBHOOK` | входящий вебхук портала 2 (как раньше) |

`PORTAL_1_WEBHOOK` больше не нужен — можно удалить.

## Первый запуск

1. Задеплоить с заполненными `P1_CLIENT_ID` / `P1_CLIENT_SECRET` (P1_REFRESH_TOKEN пустой).
2. На портале 1 нажать **«Установить»** / «Переустановить» у локального приложения.
   Bitrix24 отправит токены на `/install`, сервис их сохранит в памяти.
3. Открыть Railway Logs, найти строку:
   `SAVE THIS refresh_token to Railway env P1_REFRESH_TOKEN: <токен>`
4. Скопировать токен в Railway → Variables → `P1_REFRESH_TOKEN`. Это нужно, чтобы
   токен переживал рестарты контейнера.

После этого access_token обновляется автоматически (живёт 1 час, сервис рефрешит сам).

**Важно:** при каждом рефреше Битрикс выдаёт НОВЫЙ refresh_token (старый продолжает
действовать какое-то время, но не вечно). Сервис пишет новый токен в логи при каждом
рефреше. Если контейнер перезапустится спустя долгое время и P1_REFRESH_TOKEN протух —
просто нажмите «Переустановить» приложение на портале 1, и токены обновятся через /install.

## Триггер

Без изменений: исходящий вебхук/робот на портале 1 → `POST https://<домен>.up.railway.app/sync` (deal_id передаётся как `?deal_id={=Document:ID}` или в form-данных события).

## Диагностика

- `GET /status` — очередь, счётчики, наличие OAuth-токенов (`p1_oauth`).
- Railway Logs — построчный лог каждой синхронизации.

## Логика синхронизации

- Поле на портале 1 пустое → портал 2 не трогаем.
- Поле на портале 1 непустое → поле на портале 2 полностью заменяется.
- Нет VIN или нет сделки на портале 2 → пропуск.
- Очередь FIFO, дедупликация, ~2 req/sec троттлинг, retry с backoff.
